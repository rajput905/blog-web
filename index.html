Design · 14 Sep 2026

Why calm colors make text easier to read

Warm backgrounds and softer ink reduce glare and make long articles more comfortable to read.

Pure black text on a pure white page is the default in many browsers, and it works well for short labels and quick scanning. Over a long article, though, that contrast can feel harsh. The brightness of a white screen makes the eyes work harder, especially in a dim room or late at night. Softer colors solve much of that problem without sacrificing legibility. A warm off-white background paired with a dark brown-grey ink keeps contrast high enough for comfortable reading while lowering the overall glare.

Contrast still matters, so the goal is balance rather than softness at any cost. WCAG recommends a contrast ratio of at least 4.5 to 1 for normal body text, and any palette can be checked with a free online tool before publishing. When I choose colors for a reading page, I start with the text color and test it against the background, then adjust the accent colors so links and buttons stand out without shouting. Line length and line height matter just as much. A column of around 60 to 75 characters with a line height near 1.7 gives the eye a steady rhythm from one line to the next.

Animation · 29 Aug 2026

Animate only what helps people understand

Motion can guide attention, but too much of it turns a page into noise. Use it for feedback and key moments.

Animation is most useful when it answers a question for the visitor. A button that lifts slightly on hover tells the person that it is clickable. A panel that slides open shows where new content came from. A short fade when a section enters the screen can help the eye notice that something has changed. In each case the motion carries information, and removing it would make the interface harder to understand.

Animation becomes a problem when it competes with the content. Elements that bounce forever, text that flies in from every direction, or effects that repeat on every scroll can tire people quickly. My rule is simple: animate once, keep it short, and use transform and opacity so the browser can handle the work smoothly. Always respect the reduced-motion setting too. Some visitors feel dizziness or discomfort from movement, and a good page turns off nonessential effects for them while still showing the content clearly.

Process · 2 Aug 2026

Building a page with plain HTML and CSS

A single HTML file, one stylesheet and a few lines of JavaScript are enough for many small websites.

Frameworks are useful, but they are not required for every project. A portfolio, a local business page or a small event site can be built with one HTML file, one stylesheet and a short script. Plain files are easy to open, easy to edit and easy to hand over to someone who is not a developer. There is no build step to set up, and the page works on any hosting service that can serve static files.

The trick is to keep the structure simple and consistent. Use semantic elements like header, main, section and footer so the page makes sense to screen readers and search engines. Define colors and fonts as CSS custom properties at the top of the stylesheet, so a single change updates the whole site. Group styles by section, use class names that describe purpose rather than appearance, and keep JavaScript limited to what the page truly needs. A well-organized plain project can stay maintainable for years.

Performance · 18 Jul 2026

Designing for slow mobile networks

Many visitors use slow or unstable connections, so smaller images and fewer requests make a real difference.

Not everyone browses on a fast connection. Many people use mobile data in areas with weak signal, and a page that takes ten seconds to show its first content can lose a visitor before the design even appears. Measuring the size of the page is the first step. Images are usually the heaviest part, so it helps to resize them to the size they will be displayed, compress them, and use modern formats where the browser supports them.

Loading strategy matters too. Adding loading="lazy" to images below the fold means the browser downloads them only as the person scrolls toward them. Keeping the number of external scripts and fonts low reduces the requests needed before the page becomes usable. Some fonts can be replaced with system fonts entirely, which removes a download without hurting readability. Test on a throttled connection in your browser's developer tools to see how the page behaves when the network is slow, not just when it is fast.

Accessibility · 5 Jul 2026

Writing accessible forms

Clear labels, helpful error messages and visible focus states make forms usable for everyone.

Forms are where visitors take action, so they deserve careful attention. Every input needs a visible label connected to it, using a for attribute that matches the input's id. Placeholder text is not a replacement for a label, because it disappears as soon as someone starts typing. Using the right input type, such as email or tel, also helps phones show the correct keyboard and lets browsers check the basic format before submission.

Error messages should explain what went wrong and how to fix it. Saying "Please enter a valid email address" is far more helpful than a red border with no text. Place the message next to the field it describes, and move focus to the first invalid field after submission so keyboard users know where to go. Avoid relying on color alone to show an error, and pair it with an icon or text. Finally, keep the form as short as possible, because every extra field is one more reason for someone to leave without finishing.

Typography · 21 Jun 2026

Choosing a typeface without overthinking it

Two well-chosen fonts, one for headings and one for body text, cover most projects.

Typography can feel like a huge decision, but most projects need only two fonts. A serif or expressive display face works well for headings because it adds character and draws the eye. A clean sans-serif is usually the better choice for body text, because it stays readable at small sizes on screens. Google Fonts offers a large selection, and loading only the weights you actually use keeps the download small.

Pay more attention to size and spacing than to finding the perfect font. A body size of around 16 to 18 pixels, a line height near 1.6 to 1.7, and comfortable paragraph spacing will improve readability far more than switching between dozens of typefaces. Use a clear size scale for headings so the hierarchy is obvious. Always provide fallback fonts in your CSS, such as Georgia or system-ui, so the page still looks reasonable if the web font fails to load. Consistency across the site matters more than novelty.

CSS · 9 Jun 2026

CSS Grid or Flexbox? Use both.

Flexbox handles rows and alignment, while Grid is better for two-dimensional layouts.

Flexbox and Grid are both built into modern browsers, and they solve different problems. Flexbox arranges items in a single direction, either a row or a column. It is ideal for navigation bars, button groups and centering content inside a card. Grid works in two dimensions, controlling rows and columns together. It suits galleries, dashboards and page layouts where items need to line up in both directions.

In real projects the two often work together. A page might use Grid for the overall layout and Flexbox inside each card to align the title, text and buttons. Responsive design becomes easier with features like auto-fit and minmax, which let columns adjust to the available space without many media queries. Start with the simplest layout that works, test it at several widths, and add complexity only when the design needs it.

Accessibility · 27 May 2026

Keyboard navigation, the basics

Many people navigate with a keyboard, so every link, button and menu should be reachable and clearly focused.

A surprising number of websites cannot be used with a keyboard alone. Pressing Tab should move through links, buttons and form fields in a logical order, and the focused element should be clearly visible. Using native elements such as a, button and input gives you keyboard support for free. Building a clickable div is much harder to get right, because it needs its own focus behavior, key handlers and role information.

Focus styles are often removed by designers who find them unattractive, which makes the page unusable for keyboard users. Instead, style focus in a way that matches the design, such as a thick outline with an offset. Modal dialogs need extra care: focus should move into the dialog when it opens, stay inside while it is open, and return to the trigger when it closes. Testing is simple. Put the mouse aside for a few minutes and try to complete the main tasks of your site using only the keyboard.

JavaScript · 13 May 2026

Small JavaScript interactions that feel natural

A few well-placed scripts can improve a page without turning it into an application.

JavaScript is most helpful when it does small, focused jobs. Toggling a menu, revealing content when it scrolls into view, or validating a form before submission are all good examples. These interactions make the page respond to the visitor, but they do not need a large framework. Attaching event listeners directly to the elements involved keeps the code short and easy to follow.

Good interactions also degrade gracefully. If the script fails to load, the content should still be readable and the links should still work. Use IntersectionObserver instead of listening to every scroll event, since it is more efficient and easier to reason about. Keep animations driven by CSS where possible, and let JavaScript add or remove classes. Finally, respect the reduced-motion preference by checking it in your script and skipping effects when it is set.

Performance · 22 Apr 2026

Keeping a website fast over time

Performance is not a one-time task, because new images, scripts and fonts slowly add weight.

A website that feels fast at launch can slowly become sluggish. New images get added without being compressed, a tracking script is installed for a campaign and never removed, and a font family is loaded with more weights than anyone uses. Each change looks harmless on its own, but together they add seconds to the load time. Setting a simple budget, such as a page weight limit or a target load time, helps you notice when something has grown too large.

Regular checks keep things under control. Running a performance audit in Lighthouse or a similar tool once a month shows which files cause the most delay. Remove unused CSS and scripts, combine small requests where it makes sense, and cache static assets so returning visitors do not download them again. Most importantly, measure before and after every change. Performance improvements are easiest to maintain when they are based on numbers rather than guesses.
